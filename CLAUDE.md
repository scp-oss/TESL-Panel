# CLAUDE.md

Оперативные заметки для Claude-сессий, работающих с этим репозиторием —
плотно, для агента. Не класть сюда реальные серверные пути/домены/токены
(см. TESL-Manager/CLAUDE.md "Секреты и пути — не в git" за тот же
принцип) — реальные значения живут только в `panel.env` на сервере
(генерируется `infra/deploy.sh`, в git не попадает, см. `.gitignore`).

## Зачем этот репозиторий (создан 2026-09-23)

Прямой запрос пользователя: "давай начнём разварачивать наш сервис —
сборка на вебдав остаётся, лаунчер тоже пока в таком виде — наши
действия: поднять панель с возможностью скачать exe лаунчера и
менеджера (пока с GitHub), плюс переписанный менеджер для заливки новой
версии сборки уже мимо Nextcloud и сразу в наш сервис, путь хранилища
`/mnt/1tb-1/<название проекта>`".

Разбито на два independent, но связанных куска:
1. **Эта страница** — публичная точка входа для игроков (скачать
   TESL.exe/TESL-Manager.exe) + приёмник новых публикаций сборки.
2. **TESL-Manager получил новый транспорт** (`panel_client.py::PanelHTTP`,
   см. его собственный CLAUDE.md) — публикует напрямую сюда вместо
   Nextcloud/WebDAV, когда оператор выберет `backend: "panel"` в
   конфиге.

**Уже существующая сборка** (та, что реально стоит у игроков, чанки на
Nextcloud/WebDAV) **этим не тронута и не мигрирует** — TESL-лаунчер
по-прежнему читает её оттуда (`DAV_BASE_URL` в TESL не менялся). Эта
панель и её API — путь для БУДУЩИХ публикаций, начиная с той, что
оператор решит опубликовать через неё в первый раз. Явно НЕ входило в
этот заход (по прямому "лаунчер тоже пока в таком виде"): переключение
самого TESL-лаунчера на чтение отсюда — когда/если это понадобится,
это отдельная, более поздняя задача (симметрично уже
запланированному-но-не-включённому read-only nginx+Cloudflare плану в
TESL-Manager — та же дисциплина "построили, проверили, только потом
переключили reader").

## Архитектура

```
panel/
  app.py             — Flask routes (/, /health, /api/depot/<project>/...)
  config.py          — вся конфигурация через os.environ, ничего не хардкожено
  storage.py         — файловое хранилище на диске, content-addressed
                        (та же раскладка, что раньше писалась на WebDAV)
  github_releases.py — кэшированный lookup последнего GitHub Release
  templates/index.html
wsgi.py              — точка входа для gunicorn (см. infra/tesl-panel.service.template)
infra/
  deploy.sh                        — идемпотентный сетап (venv+systemd+nginx),
                                      запускать на сервере, НЕ отсюда
  tesl-panel.service.template      — systemd unit (плейсхолдеры __X__)
  nginx-tesl-panel.conf.template   — nginx reverse-proxy (плейсхолдеры __X__)
```

**У Claude-сессии нет exec-доступа к продакшену** — тот же принцип, что
во всех остальных репозиториях этого проекта (z2r_autobench,
z0r-panel, TESL, TESL-Manager). `infra/deploy.sh` только готовится
здесь и передаётся оператору для ручного запуска (root по SSH).

## API депо (`/api/depot/<project>/...`)

- `GET/HEAD /api/depot/<project>/<rel_path>` — публичное чтение, токен
  НЕ нужен (тот же принцип, что у read-only nginx-плана в
  TESL-Manager: чтение депо — не секрет).
- `PUT /api/depot/<project>/<rel_path>` — запись, требует
  `Authorization: Bearer <TESL_PANEL_UPLOAD_TOKEN>`. Тело запроса —
  сырые байты файла, пишется атомарно (temp-файл + `os.replace`) —
  читающий никогда не увидит частично записанный файл.
- `GET /api/depot/<project>/chunks` — список всех `chunk_id`, уже
  лежащих в `chunks/` этого проекта (для delta-сравнения на стороне
  клиента, аналог `NextcloudDAV.list_chunk_ids()`).
- `GET /api/depot/<project>/test` — проверка достижимости + (неявно,
  через отдельный `PUT`-запрос до этого) валидности токена.

## Живой инцидент: SQLite-версия `builds_db.py` уронила прод — сервер собран без `_sqlite3` (2026-09-23)

При первом реальном деплое сборок-как-объектов (см. следующий раздел)
сервис на Server A не стартовал вообще —
`journalctl -u tesl-panel.service`:

```
ModuleNotFoundError: No module named '_sqlite3'
```

`_sqlite3` — C-расширение, часть stdlib `sqlite3`, компилируется В
интерпретатор на этапе сборки Python (нужен `libsqlite3-dev` в системе
на момент `./configure && make`). На Server A `python3` (`/usr/local/
lib/python3.11`) оказался собран из исходников (не Debian-пакет — тот
почти всегда тянет sqlite поддержку как зависимость), без этого
заголовка в системе на момент сборки — `import sqlite3` падает сразу
на импорте `panel/app.py`, gunicorn-воркер не может загрузить WSGI-
приложение вообще, `systemctl` уходит в бесконечный auto-restart.

**Первая попытка исправить это была неверной и откачена**: переписать
`builds_db.py` на обычный JSON-файл вместо `sqlite3`, раз этому модулю
на тот момент реально не требовался JOIN/агрегации. Прямое возражение
пользователя: SQL остаётся нужен не для сегодняшнего состояния модуля,
а как фундамент под уже запланированное — несколько РЕЛИЗОВ/версий на
каждую сборку и откат на клиенте на конкретную прошлую версию. Это
история строк и связи между таблицами, которые JSON-с-перезаписью-
целиком не выражает естественно, а вторая самодельная мини-БД поверх
файла — это ровно то усложнение, которого SQLite и существует, чтобы
избежать.

**Правильное исправление: `builds_db.py` остаётся на SQLite, но
пробует stdlib-модуль первым и откатывается на `pysqlite3-binary`
(PyPI-пакет, не stdlib) только если тот недоступен:**
```python
try:
    import sqlite3
except ImportError:
    import pysqlite3 as sqlite3
```
`pysqlite3-binary` — самодостаточное wheel со своим статически
слинкованным `libsqlite3` внутри пакета; ему не нужно, чтобы СИСТЕМНЫЙ
Python был собран с sqlite-поддержкой, он просто тащит свою копию —
ставится обычным `pip install` в venv, который и так уже делает
`deploy.sh`, exec-доступ на сервер для этого не нужен. Добавлен в
`requirements.txt` безусловно (не под каким-то маркером — pip не умеет
"поставь пакет, только если такого-то stdlib-модуля нет"), но
безвреден и на нормальном Python: код всегда сначала пробует stdlib
`sqlite3`, берёт `pysqlite3` только как fallback. Проверено локально:
симуляция `ImportError` на `sqlite3` → `pysqlite3` действительно
подхватывается, `sqlite3.connect(':memory:')`/`CREATE TABLE`/`INSERT`/
`SELECT` через него работают идентично. Реальный `sqlite3` на этом
сервере (dev-окружение) есть, так что здесь используется прямой путь —
fallback реально понадобится только на Server A и любом другом сервере
с той же нестандартной сборкой Python.

**Публичная сигнатура функций `builds_db.py` не менялась вообще** — SQL-
схема (`_connect()`, все запросы) идентична исходной версии до этого
инцидента, только добавлен `try/except` вокруг `import sqlite3` в самом
верху файла. `storage.py`/`app.py`/клиентская сторона (TESL-Manager) как
не знали, так и не знают, чем это хранится.

**Урок**: прежде чем добавлять в этот проект НОВУЮ stdlib-зависимость,
которая может требовать нестандартной сборки интерпретатора (`sqlite3`,
`ssl`, `zlib`, `lzma`, `bz2`, `curses`, `tkinter` — все они опциональны
на этапе сборки Python и тихо отсутствуют, если системе на тот момент
не хватало соответствующего `-dev`-пакета) — не обязательно избегать
её, если задача реально хочет то, что она даёт (как здесь — будущие
релизы/версии/откат), но нужно сразу закладывать реальный, проверенный
PyPI-fallback (тот же паттерн `try: import X / except ImportError:
import X_binary as X`, если для нужного модуля есть самодостаточная
wheel-версия), а не менять сам выбор хранилища при первом же таком
падения. `requirements.txt` сам по себе такие проблемы не ловит (`pip
install X` не чинит отсутствие STDLIB-модуля `X`) — но пакет вроде
`pysqlite3-binary`, который целиком заменяет собой то, чего не хватает,
и есть та защита, которую можно туда добавить.

## Разделы "Отчёты" и "Дашборд" (2026-09-23)

Два прямых запроса пользователя подряд.

### Отчёты (`reports_storage.py`, `/admin/reports/...`, `/api/reports/...`)

- Два вида — ровно то, что TESL-лаунчер уже умеет отправлять (см.
  `TESL/launcher/core/crash_logger.py`/`debug_log.py`): крэш-репорты
  Skyrim и лог отладки лаунчера, сейчас идут на WebDAV напрямую
  (`CRASH_LOG_REMOTE_PATH`/`DEBUG_LOG_REMOTE_PATH`), не сюда.
  **Лаунчер этим заходом НЕ трогается** — стоящая инструкция
  пользователя (см. TESL-Manager/CLAUDE.md, "TESL (лаунчер) — пока не
  трогаем его пока на второй ПК не скачаю сборку старую") — эта панель
  получает готовую-принять-отчёты инфраструктуру плюс саму страницу
  просмотра, переключение реального транспорта лаунчера сюда —
  отдельный, более поздний шаг.
- Раскладка на диске (`<STORAGE_ROOT>/_reports/<report_type>/<username>/
  <timestamp>/<filename>`) намеренно копирует уже действующую на WebDAV
  структуру `<remote_path>/<username>/<timestamp>/` 1:1 — если/когда
  транспорт переключат, раскладка не меняется, меняется только клиент,
  который её пишет.
- `PUT /api/reports/<type>/<username>/<timestamp>/<filename>` (Bearer,
  тот же токен, что депо) — та же форма, что и `depot_object`, ради
  единообразия. Ничем пока не вызывается.
- `/admin/reports` (сводка по двум типам с числом отчётов) →
  `/admin/reports/<type>` (список пользователей) →
  `/admin/reports/<type>/<username>` (список меток времени) →
  `/admin/reports/<type>/<username>/<timestamp>` (список файлов,
  скачивание, удаление отчёта целиком) — обычная сессия `/admin`, без
  Bearer.
- Валидация сегментов пути (`_SEGMENT_RE`, буквы/цифры/`_`/`.`/`-`) —
  тот же принцип, что и `builds_db._NAME_RE`, но `username`/`timestamp`
  здесь приходят от лаунчера (когда реально подключат), не только от
  доверенного оператора через панель — валидируется строже, не только
  на уровне Flask URL routing.

### Дашборд (`system_stats.py`, `/admin/dashboard`)

- Место на выбранном диске + состояние, график сети (загрузка/
  выгрузка), загруженность CPU/ОЗУ.
- **Без `psutil`** — читает `/proc/*` напрямую (`/proc/mounts` для
  списка дисков, `/proc/stat` для CPU, `/proc/meminfo` для памяти,
  `/proc/net/dev` для сети) — проект держит минимум зависимостей (см.
  "Стиль" ниже), а `/proc` и так единственный источник правды на этой
  конкретной целевой платформе (`infra/deploy.sh` — systemd/apt/Debian),
  переносимость на не-Linux этому сервису не нужна.
- `cpu_percent()` блокирует запрос на ~0.2с (два замера `/proc/stat` с
  паузой между ними, тот же принцип, что у `top`) — приемлемо для
  редкого admin-опроса дашборда, НЕ на горячем пути раздачи депо (тот
  вообще не трогает `system_stats.py`).
- **Скорость сети считается на клиенте, не на сервере** —
  `network_counters()` отдаёт сырые накопительные `rx`/`tx` байты,
  `dashboard.html`'s JS хранит предыдущий замер и делит разницу на
  разницу времени между двумя опросами. Намеренно НЕ хранит "предыдущий
  замер" на сервере — под несколькими gunicorn-воркерами следующий
  запрос мог бы попасть на другой воркер с другим (или вообще
  отсутствующим) состоянием, а клиентское состояние одно на открытую
  вкладку и всегда консистентно само с собой.
- График — обычный `<canvas>` + ручная отрисовка (две линии, синяя
  `--accent` для входящего/загрузки, зелёная `--ok` для исходящего/
  выгрузки — те же токены, что уже использует остальной UI панели,
  не отдельная библиотечная палитра), без сторонней JS-библиотеки —
  тот же принцип минимума зависимостей, что и на бэкенде. Опрос раз в
  2с, скользящее окно 40 точек.
- **Проверено**: `Flask.test_client()` — обе страницы отдают 200,
  `/admin/dashboard/stats` возвращает реальные метрики (запускалось не
  в мок-окружении, а против самой песочницы сессии).

## `builds_db.py` — реестр сборок, id вместо имени как ключ (2026-09-23)

**Поправка того же дня, см. раздел выше "Живой инцидент: SQLite-версия
builds_db.py уронила прод"** — изначально сделано на SQLite (как
непосредственно описано ниже), на реальном сервере это уронило сервис
(`_sqlite3` не собран в тамошний Python). Первая реакция (переписать на
JSON-файл) была неверной и откачена по прямому требованию пользователя —
SQL нужен не ради сегодняшних запросов, а как фундамент под уже
запланированные несколько релизов/версий на сборку с откатом на клиенте.
**Итог: `builds_db.py` остаётся на SQLite** (весь текст этого раздела —
id как реальный ключ, что заменяет, почему на диске имя и т.д. — верен
как есть), просто с fallback-импортом на `pysqlite3-binary`, если
stdlib `sqlite3` недоступен (см. раздел про инцидент для деталей и как
это проверено).

Прямой запрос пользователя: "проект в панели и в менеджере не надо
указывать как ключ, т.к. проекты мы создаём и в панели, и в менеджере...
к панели может придётся прикрутить БД... сборки — это объекты внутри".
Решение (тоже прямой запрос, после уточняющего вопроса): "полноценно —
SQLite в панели, id — реальный ключ".

- **`builds_db.py`** (новый) заменяет `projects.py` (удалён) — таблица
  `builds (id, name, created_at, updated_at)` в SQLite-файле
  `<STORAGE_ROOT>/_meta/builds.db` (`sqlite3`, с fallback на
  `pysqlite3-binary` — см. отдельный раздел про живой инцидент). Новое
  соединение на каждый вызов под `threading.Lock()` — эта БД живёт
  только на пути управления сборками (list/create/delete/rename), НЕ на
  горячем пути записи/чтения чанков (тот остаётся чистой файловой
  операцией в `storage.py`, без единого обращения к БД) — при
  нескольких gunicorn-воркерах так безопаснее (нет расшаренного
  состояния в процессе) и частота вызовов низкая, постоянное соединение
  не оправдано.
- **Явно НЕ то же самое, что `chunk_index.db`** (`pack_writer.py` в
  TESL-Manager, живёт внутри `<build_dir>/chunk_index.db`, per-build,
  решает "где физически лежит чанк внутри pack-файлов") — пользователь
  специально уточнил это при подтверждении объёма работы ("задумка с
  локальной бд для сборки остаётся"), этот файл её не трогает и не
  заменяет, они по разным вопросам.
- **Имя сборки остаётся именем папки на диске** — переименовывать уже
  опубликованные деревья чанков без доступа к реальному серверу было
  бы рискованно (нет exec-доступа к продакшену, тот же принцип, что и
  везде в этом проекте). `rename_build()` в БД + `storage.rename_dir()`
  на диске идут одним вызывающим заходом (`app.py`) — имя-в-реестре и
  имя-как-путь никогда не расходятся.
- **`_migrate_legacy_if_needed()`** — при первом обращении к пустой
  `builds.db` читает старый `<STORAGE_ROOT>/_meta/projects.json` (если
  есть) и выдаёт каждому имени свежий UUID, СОХРАНЯЯ его директорию на
  месте — уже опубликованные на реальном сервере сборки (в частности
  `TESVAE`) продолжают резолвиться, просто с этого момента у них
  появляется id. Идемпотентно (если в `builds` уже есть хоть одна
  строка — не трогает), не удаляет и не читает `projects.json` повторно
  после первого раза.
- **API стал build_id-адресным**: `/api/depot/<project>/...` →
  `/api/depot/<build_id>/...`, `/api/projects` → `/api/builds` (GET
  список, POST создать, DELETE `/api/builds/<id>` удалить, PATCH
  `/api/builds/<id>` переименовать — все три Bearer-защищены, GET
  список публичный). **Это ломающее изменение для уже настроенного
  TESL-Manager** — старый URL по имени (`/api/depot/TESVAE/...`) теперь
  404 (имя — не валидный id). Единственный реальный пользователь этой
  панели должен один раз заново выбрать сборку в GUI (комбобокс сам
  подтянет список и покажет реальные id) — см. TESL-Manager's CLAUDE.md
  за то, как клиентская миграция обрабатывает именно этот случай.
- **`/admin`-маршруты остались по ИМЕНИ в URL** (`/admin/project/<name>/
  ...`) — читать глазами `/admin/project/a1b2c3d4.../files` не хотелось
  бы, и не нужно: обработчики резолвят имя → build_id внутри себя
  (`builds_db.get_build_by_name()`), а не наружу — так что человеческая
  часть UI не изменилась вообще, только программный API. `project_detail.
  html` получил поле переименования (тот же `rename_build()`) — id
  показывается тут же, только для информации.
- **Проверено**: `Flask.test_client()`, полный сквозной сценарий —
  legacy `projects.json` (с реальным уже-опубликованным деревом чанков)
  → миграция при первом `GET /api/builds` → старый name-адресный `/api/
  depot/TESVAE/...` корректно 404, новый id-адресный работает → создание/
  PUT файла/чтение/переименование через `/api/builds/<id>` PATCH
  (папка физически переехала, файл всё ещё читается по тому же id) →
  admin UI (список/деталка/переименование форма/удаление) → 401 без
  токена на все мутирующие ручки.

## Self-update панели из `/admin/settings` (2026-09-23)

Прямой запрос пользователя: кнопка обновить саму панель, если доступна
новая версия, в её собственных настройках.

- **Проверка** (`self_update.check_for_updates()`) — ничего не пишет:
  `git rev-parse HEAD` (локально) + `git ls-remote origin HEAD` (сеть,
  БЕЗ побочного эффекта записи в `.git`, в отличие от `git fetch`).
  Выбрано намеренно из-за прав на диске: `deploy.sh` оставляет сам
  чекаут во владении того, кто его склонировал (обычно root), сервисный
  пользователь `tesl-panel` получает только `o+rX` (чтение+исполнение,
  см. `chmod -R o+rX "$PROJECT_DIR"` в `deploy.sh`) — `git fetch`/`pull`
  от его имени напрямую упали бы на попытке создать lock-файл в `.git/`.
- **Применение** (`self_update.apply_update()`) — `git pull --ff-only`
  через `sudo -n`, затем fire-and-forget `systemctl restart
  tesl-panel.service` (тем же sudo) — ответ HTTP собирается и
  отправляется ДО рестарта, поскольку рестарт убивает сам обрабатывающий
  запрос процесс.
- **`NoNewPrivileges=true` снято из systemd-юнита** (было в
  `tesl-panel.service.template`) — конфликтует с самой идеей sudo:
  `sudo` — setuid-бинарник, `NoNewPrivileges=true` запрещает ЛЮБУЮ
  эскалацию через setuid/setcap, включая легитимную через sudoers.
  Реальный trade-off, не тихая дыра: сервис и так уже мог писать любой
  файл под `STORAGE_ROOT` (это его основная работа — приём чанков), а
  sudo добавляет ровно ДВЕ явно перечисленные в `/etc/sudoers.d/
  tesl-panel-self-update` команды (`git -C <repo> pull --ff-only` и
  `systemctl restart tesl-panel.service`), не root целиком.
- **`deploy.sh`** ставит этот sudoers-файл идемпотентно на каждом
  запуске (`visudo -cf` на временный файл ПЕРЕД установкой, `install -m
  440`, тот же принцип "проверить перед заменой рабочего", что и
  `ensure_panel_runtime_grants` в z2r_autobench использует для своих
  грантов) — существующие деплои получат его при следующем `git pull &&
  sudo ./infra/deploy.sh ...`, до этого кнопка "Обновить и
  перезапустить" будет честно отвечать "нет прав на sudo" вместо
  тихого зависания.
- Кнопка обновления показывается только когда проверка нашла реальное
  расхождение (`update_info.up_to_date == False`) — сама проверка не
  выполняется на каждой загрузке `/admin/settings` (только по кнопке
  "🔍 Проверить обновления"), чтобы не дёргать GitHub при каждом заходе
  на страницу настроек.
- Проверено `Flask.test_client()` с замоканными `self_update.
  check_for_updates`/`apply_update` (актуально/есть обновление/успех/
  отказ — все четыре ветки рендера), плюс реальный
  `check_for_updates()` — против настоящего репозитория и GitHub из
  песочницы (`git ls-remote origin HEAD` действительно отработал).

## Projects/Files API (JSON, для десктоп-GUI TESL-Manager, 2026-09-23)

Добавлено под конкретную нужду TESL-Manager'а: `depot_tab.py` там
получил серверный выбор проекта вместо ручного ввода строки, плюс
отдельная вкладка "🗂️ Файлы на депо" (десктоп-эквивалент здешнего
`/admin/project/<name>/files`, но без cookie-сессии) — см. TESL-Manager's
CLAUDE.md за подробности GUI-стороны.

- `GET /api/projects` — публичное чтение, список имён (`projects.
  list_projects()`), токен не нужен (тот же принцип, что у GET/HEAD
  `depot_object`).
- `POST /api/projects` — Bearer, тело `{"name": "..."}` (JSON) или
  form-поле `name`; `projects.add_project()` — та же валидация
  (`[A-Za-z0-9_-]{1,64}`), что и `/admin/add-project`, 400 при
  недопустимом имени, 201 при успехе (идемпотентно — уже существующее
  имя тоже 201).
- `GET /api/depot/<project>/files` — Bearer (не публичный — тот же
  уровень доверия, что у `/admin/.../files`, только без сессии),
  JSON `{"files": [{"path": ..., "size": ...}, ...]}` —
  `storage.list_files()` без изменений, просто новый JSON-фасад.
- `DELETE /api/depot/<project>/<rel_path>` — Bearer, тот же URL, что
  уже существующие GET/HEAD/PUT на `depot_object` (не отдельный роут,
  просто новый метод) — `storage.delete_file()`, идемпотентно
  (`{"existed": false}`, не ошибка, при повторном вызове).

`project` — allowlist (`config.ALLOWED_PROJECTS`, `TESL_PANEL_PROJECTS`
через запятую), не принимается как произвольная строка — двойная
защита от path traversal: (1) на уровне имени проекта здесь, (2) на
уровне пути внутри проекта в `storage.safe_path()` (`realpath` +
prefix-check, тот же паттерн, что z2r_autobench's
`domain_list_sync.sh --path` применяет к своим путям).

## Почему `mkcol()` — no-op в `PanelHTTP` (см. TESL-Manager/panel_client.py)

`NextcloudDAV` (WebDAV) требует явного `MKCOL` перед `PUT` в
несуществующую директорию — WebDAV-протокол так устроен. Файловое
хранилище на диске (`storage.put_bytes()`) создаёт родительские папки
сама (`path.parent.mkdir(parents=True, exist_ok=True)`) при каждом
`PUT` — отдельный вызов для "создать папку" просто не нужен. `PanelHTTP.
mkcol()` всё равно существует и возвращает `True` — чтобы
`DepotSyncManager.ensure_depot_structure()`/`_ensure_chunk_subdir()` не
знали и не заботились, какой транспорт сейчас активен (см. depot_sync_
manager.py `_get_dav()` — единственное место, которое вообще смотрит на
`backend`).

## TLS — Cloudflare Origin Certificate, НЕ certbot (live-инцидент, 2026-09-23)

Живая ошибка при первом реальном деплое: до того, как это правило было
явно сформулировано, `certbot --nginx -d <домен>` был запущен ОТДЕЛЬНО,
до `infra/deploy.sh` (когда ещё не существовало отдельного nginx-файла
под этот домен). Certbot нашёл единственный подходящий сайт по
умолчанию — **`/etc/nginx/sites-enabled/default`** (стандартная
Debian-заглушка) — и вписал туда домен панели: продублировал весь
блок в новый 443-server (с `ssl_certificate`/`ssl_certificate_key`) и
добавил в исходный 80-блок `if ($host = ...) { return 301 ...; }`
редирект. Когда следом реально отработал `deploy.sh` и создал СВОЙ,
отдельный конфиг с тем же `server_name` — nginx увидел дублирующийся
`server_name` на 80/443 и один из двух молча проигнорировал
("conflicting server name ... ignored" в выводе `nginx -t`), то есть
домен продолжал резолвиться в старую (сертботовскую, никуда не
проксирующую) заглушку, а не в реальный сервис.

**Root cause, шире одного инцидента**: порты 80/443 на этом сервере
УЖЕ заняты несколькими другими проектами (`nethunter.sytes.net` и
другие, см. TESL-Manager/CLAUDE.md "Секреты и модель угроз" за
аналогичное правило "не трогать") — certbot трогать нельзя было вообще,
тот же принцип, что уже применялся к отдельному read-only nginx-плану
в TESL-Manager (`nginx-depot-read.conf.template` — Cloudflare Origin
Cert вместо certbot, именно по этой причине). Просто не был перенесён
сюда сразу при создании репозитория — упущение при копировании
паттерна, не сама Cloudflare-архитектура была под вопросом.

**Исправлено**: `nginx-tesl-panel.conf.template`/`deploy.sh` теперь
требуют Cloudflare Origin Certificate (`--cert`/`--key`, по умолчанию
`<repo>/ssl/origin.{pem,key}`, `ssl/` в `.gitignore`) — `deploy.sh`
ОТКАЗЫВАЕТСЯ работать, если файлы не найдены, вместо того чтобы молча
продолжить без TLS. certbot нигде в этом репозитории больше не
упоминается как рабочий путь.

**Восстановление после уже случившегося инцидента** (руками на
сервере, не автоматизировано — правка структуры `sites-enabled/default`
достаточно чувствительна, чтобы делать её только с подтверждённым
содержимым файла, не вслепую): certbot добавил РОВНО два новых
`server{}`-блока поверх оригинального содержимого `default` — они
идентифицируются по `# managed by Certbot` на части строк и по
дублированию `server_name`/`root /var/www/html`/`location /` из
оригинального блока. Оригинальный дефолтный блок и закомментированный
пример-вхост (в начале файла) certbot не трогал — их каждый раз нужно
оставлять как есть, удалять только сертботовские блоки целиком (обычно
это последние два `server{}` в файле, каждый со своим "managed by
Certbot" маркером на части строк).

## `/admin/settings` — "код настройки" для TESL-Manager (2026-09-23)

Прямой запрос пользователя: вместо того, чтобы вводить URL панели и
upload-токен в TESL-Manager по отдельности, панель сама генерирует ОДНУ
строку ("код настройки"), пользователь копирует её сюда один раз и
вставляет в клиент — GUI сам разбирает её и подключается, больше
ничего для авторизации вводить не нужно.

- `_generate_setup_code()` (`app.py`) — `base64(json.dumps({"v": 1,
  "base_url": ..., "token": config.UPLOAD_TOKEN}))`, без переносов/
  пробелов внутри — единственная строка, которую можно целиком
  скопировать и вставить одним действием. `base_url` — из нового
  `config.PUBLIC_BASE_URL` (env `TESL_PANEL_PUBLIC_URL`), если задан,
  иначе `request.url_root` на лету (работает и без явной настройки,
  поскольку админ и так заходит через реальный публичный домен за
  Cloudflare).
- Не является отдельным секретом сам факт base64-кодирования — это
  просто способ упаковать несколько полей в одну строку без разделителей,
  которые могли бы потеряться при копировании. Секрет внутри — тот же
  `UPLOAD_TOKEN`, что уже используется для `/api/depot/*` записи и для
  входа в `/admin` — тот же уровень доверия, что и всегда в этом
  репозитории (см. "Почему один токен и для записи, и для admin-логина"
  в комментариях `config.py`), просто теперь в удобной для копирования
  форме. Страница `settings.html` явно предупреждает об этом текстом
  рядом с полем.
- `GET /admin/settings` (новый маршрут, `@_admin_required`, та же
  сессия, что и остальной `/admin`) — рендерит `templates/settings.html`
  с готовым кодом в `<textarea readonly>` + кнопка "📋 Скопировать"
  (`navigator.clipboard.writeText`, с фолбэком на `document.execCommand
  ('copy')` для старых браузеров/не-HTTPS контекстов). Если
  `UPLOAD_TOKEN` не сконфигурирован на сервере — жёлтое предупреждение
  сверху страницы вместо тихой генерации кода с пустым токеном
  (который бы просто не сработал на клиенте, без объяснения почему).
- Ссылка на страницу — в топбаре `admin.html` ("настройки" рядом с
  "выйти"), единственная точка входа, как и просил пользователь
  ("в самой панели добавь пункт настройки").
- Клиентская сторона (`decode_setup_code()`/`encode_setup_code()`) —
  `TESL-Manager/depot_sync_manager/panel_client.py`, см. его CLAUDE.md.
  Формат зеркалится вручную между двумя репозиториями (разные языковые
  рантаймы, общий модуль тут не оправдан) — если формат `_generate_
  setup_code()` здесь когда-нибудь изменится, поменять `decode_setup_
  code()` на стороне клиента тем же заходом, иначе старые код настройки
  перестанут разбираться молча (там уже сделано мягко — `decode_setup_
  code()` возвращает `None` на любую ошибку разбора, а не падает).
- Проверено `Flask.test_client()`: логин → `/admin/settings` → код в
  `<textarea>` → `base64.b64decode` + `json.loads` даёт корректные
  `base_url`/`token`.

## Вход одной ссылкой — `/admin/login?token=<UPLOAD_TOKEN>` (2026-09-23)

Прямой запрос: удобная ссылка для входа, без открытия формы и ручного
ввода токена каждый раз (`https://.../admin/login?token=...`) — тот же
случай, что и код настройки выше, просто для человека-администратора,
а не для TESL-Manager.

- `GET /admin/login` теперь читает `token` из query-параметра (не
  только из POST-формы, как раньше): валидный токен сразу проставляет
  `session["admin"]`, redirect на `next` (тоже query-параметр) или на
  `/admin`, как обычный логин. Невалидный токен — 401 + та же страница
  логина с ошибкой, как и у формы. **Без параметра `token` поведение
  не изменилось** — обычная форма для ручного ввода, как раньше;
  POST-логин (форма) не трогался вообще, работает как и работал.
- Тот же уровень доверия к токену, что и везде в проекте (Bearer у
  `/api/*`, тот же секрет в открытом виде на `/admin/settings`) — ссылка
  с токеном в query-параметре не более "утечкоопасна", чем то, что уже
  явно показывается на этой же странице настроек; если позже понадобится
  ужесточить (например, разово используемые ссылки), пересматривать
  вместе с той же логикой.
- Проверено `Flask.test_client()`: валидный `?token=` → 302 на `/admin`
  → сессия реально авторизована; невалидный → 401, сессия не создаётся;
  без параметра — обычная форма, как раньше; `?next=` работает так же,
  как и у POST-формы; существующий POST-логин прогнан отдельно тем же
  тестом и не сломан.

## `TESL_PANEL_DOMAIN` — теперь реально используется как fallback для `PUBLIC_BASE_URL` (2026-09-23)

Живой найденный пробел, тем же вечером: `deploy.sh` принимает `--domain`
и пишет его в переменную `$DOMAIN` для генерации nginx-конфига, но
**никогда не сохранял это значение в `panel.env`** — само Flask-
приложение (`config.py`) про `TESL_PANEL_DOMAIN` не знало вообще, не
читало эту переменную. Пользователь вручную дописал
`TESL_PANEL_DOMAIN=...` в `panel.env` через `nano` на реальном сервере
(Server A) ожидая, что это на что-то влияет — не влияло. Прямой запрос
после того, как это вскрылось: "добавь [использование] TESL_PANEL_DOMAIN
в env".

- `config.py::PUBLIC_BASE_URL` — теперь берёт значение в таком порядке:
  явный `TESL_PANEL_PUBLIC_URL` (если задан, как и раньше, приоритет за
  ним — для случаев, когда одного домена недостаточно, см. комментарий
  над этим блоком) → иначе `https://<TESL_PANEL_DOMAIN>`, если задан →
  иначе `""` (прежнее поведение, `request.url_root` на лету внутри
  `_generate_setup_code()`). Схему `https://` добавляем сами и не даём
  задать её через `TESL_PANEL_DOMAIN` — этот деплой всегда живёт за
  Cloudflare Full (strict) + nginx (см. раздел про TLS выше), HTTP как
  публичная схема здесь никогда не используется, лишний параметр для
  выбора схемы был бы неоправданным усложнением.
- `infra/deploy.sh` теперь дописывает `TESL_PANEL_DOMAIN=$DOMAIN` в
  генерируемый `panel.env` (раньше эта строка вообще не попадала в
  файл) — так что при следующем `git pull && ./infra/deploy.sh --domain
  ...` переменная появится в `panel.env` автоматически даже без ручной
  правки через `nano`, и будущие свежие установки получают её сразу,
  без отдельного шага. Значение перезаписывается текущим `--domain`,
  когда он передан явно (см. следующий раздел — с 2026-09-23 он
  необязателен на повторных запусках).
- Проверено: юнит-тест `config.py` на все 4 комбинации (ничего не
  задано → `""`; только `TESL_PANEL_DOMAIN` → `https://<домен>`; оба
  заданы → побеждает `TESL_PANEL_PUBLIC_URL`; только `TESL_PANEL_PUBLIC_URL`
  → поведение как было) плюс сквозной `Flask.test_client()` — код
  настройки на `/admin/settings` при заданном только `TESL_PANEL_DOMAIN`
  реально содержит `base_url: "https://<домен>"` после
  `base64`+`json.loads`. Плюс `bash -n infra/deploy.sh`.

## `deploy.sh --domain`/`--storage-root` необязательны на повторном запуске (2026-09-23, тем же вечером)

Прямой запрос сразу после раздела выше: пользователь запустил `sudo
./infra/deploy.sh` без флагов вообще (ожидая, что раз всё уже есть в
`panel.env`, скрипт сам разберётся) — раньше это падало сразу на
`if [[ -z "$DOMAIN" || -z "$STORAGE_ROOT" ]]`, до того, как скрипт
вообще пытался заглянуть в `panel.env`.

- Добавлен fallback ПЕРЕД этой проверкой: если `--domain`/
  `--storage-root` не переданы явно, а `panel.env` уже существует —
  значения читаются оттуда (`TESL_PANEL_DOMAIN`/
  `TESL_PANEL_STORAGE_ROOT`), тем же `grep -oP`, что уже используется
  ниже для `UPLOAD_TOKEN`/`SECRET_KEY`. Печатает явно, откуда взял
  значение (`-> --domain не передан, беру из panel.env: ...`) — чтобы
  не выглядело так, будто скрипт молча угадал.
- **Явно переданный флаг по-прежнему побеждает** — это не "теперь
  всегда игнорировать флаги", а "не заставлять указывать их заново,
  если ничего не меняется". Передавать `--domain`/`--storage-root`
